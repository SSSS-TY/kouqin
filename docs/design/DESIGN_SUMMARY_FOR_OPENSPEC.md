## 1. 背景与目标

《三角洲行动》游戏内有乐器类道具「口琴」。用户希望有一个桌面工具：**照着乐谱，自动在游戏内演奏**，
并提供 UI 用于曲谱选择、导入/导出，后续逐步完善。

### 1.1 成功的样子（用户视角）

1. 打开界面，从曲谱库里选一首曲子（或粘贴一段简谱）。
2. 界面告诉他：这段谱能不能完整演奏（有没有超出乐器音域的音）。
3. 点「开始」，切到游戏、拿出游戏内的口琴道具，曲子自动演奏出来，音高对、节奏对。
4. 暂停 / 继续 / 停止随时可用；停止后不会留下按住的键。
5. 曲谱可以导出成文件分享，也可以再导入回来，内容不变。

### 1.2 v1 范围

**做**：曲谱库与编辑、导入/导出、简谱解析、演奏计划编译、播放引擎（Python 注入）、播放控制、键位校准、单元测试。

**不做（v1 明确排除）**：和弦/多声部（口琴为单音）、音频合成试听、曲谱图片/PDF 识别、云同步与分享、
录制模式、「跟着我手动弹奏录成谱」。

## 2. 已知事实与未知

### 2.1 乐器行为（**2026-09-25 游戏内实测确认**）

关键发现：**游戏 UI 会标出每个按键当前对应的简谱**（含八度点与升号）。用户据此读出了完整映射：

| 输入 | 游戏内标注 | 结论 |
|------|-----------|------|
| `z x c v b n m` | `1 2 3 4 5 6 7` | 中音区大调音阶 |
| `,` | `1̇`（数字上方带点） | 高八度 `1` |
| 按住**鼠标左键** | `1̲ … 7̲` + `1`（无点） | 整体**降一个八度** = **−12 半音** |
| 按住**鼠标滚轮（中键）** | `#1 #2 … #7` + `#1̇` | 整体**升半音** = **+1 半音** |
| 按住**鼠标右键** | `1̇ … 7̇` + `1̈`（两点） | 整体**升一个八度** = **+12 半音** |
| 按住**左键 + 中键**（同时） | 低音 `1̲…7̲` 全部带 `#` + 中音 `#1` | 两个修饰键**效果相加** = **−11 半音** |
| 按住**右键 + 中键**（同时） | 高音区全部带 `#` | 两个修饰键**效果相加** = **+13 半音** |
| **长按**任意键 | 声音持续并渐强 → 出现「波浪感」（模拟一口气的末段）→ 逐渐变小直至消失 | **长音会自然衰减**，不能靠一直按住来无限延长（§5.2 规则 5） |

> 用户最初口述的「降调 / 升调」实为**八度**升降，「半音」即半音；修饰键是**按住生效**，
> 且作用于当时所按的键（不是切换模式）。**修饰键效果可叠加**（左+中 = −11、右+中 = +13），
> 据此低音区与高音区的变化音都补齐了（见 §3.2）。

| 编号 | 结论 | 证据（2026-09-25） |
|------|------|--------------------|

## 3. 乐器模型

### 3.1 音高空间

内部一律用**相对半音偏移** `s` 表示音高，基准 = `z` 键发出的音（简谱中音 `1`，记为 `s = 0`）。

- 音级 → 半音：`1..7` → `0, 2, 4, 5, 7, 9, 11`（大调音阶）
- 八度：每个 `'` 或 `,` 标记 ±12 半音
- 变化音：`#` = +1，`b` = −1

不使用 MIDI 音高作为内部主键，避免引入「基准音到底是 C4 还是别的」这类未确认前提；
`@key C` 之类元信息只用于显示与导出。

### 3.2 可达音高集合（据实测计算）

```
可达 = { key_semitone(key) + set_offset(modifier_set) : key ∈ 键位表, modifier_set ∈ 允许的修饰组合 }
key_semitone(key) = 音级半音(key.degree) + 12 × key.octave
音级半音 = { 1:0, 2:2, 3:4, 4:5, 5:7, 6:9, 7:11 }
set_offset = 组合内各修饰键偏移之和（实测可叠加）
```

允许的修饰组合（`config/instrument.json` 的 `modifier_sets`）与它们带来的音：

| 修饰组合 | 偏移 | 由此得到（相对中音 `1` 的半音数） | 状态 |
|----------|------|-----------------------------------|------|
| 无 | 0 | `0, 2, 4, 5, 7, 9, 11, 12`（中音 1–7、高音 1̇） | 已实测 |
| 左键 | −12 | `−12, −10, −8, −7, −5, −3, −1, 0`（低音 1–7、中音 1） | 已实测 |
| 中键 | +1 | `1, 3, 5, 6, 8, 10, 12, 13`（基础键整体升半音） | 已实测 |
| 右键 | +12 | `12, 14, 16, 17, 19, 21, 23, 24`（高音区、两点 1） | 已实测 |
| **左 + 中** | **−11** | `−11, −9, −7, −6, −4, −2, −1, 1`（低音区全部加 `#`） | 已实测 |
| 中 + 右 | +13 | `13, 15, 17, 18, 20, 22, 24, 25`（高音区加 `#`） | 已实测 |

实测结论：

**`−12 … +24`（低音 `1` 到两点 `1`）共 37 个半音全部可达**，即**三个八度的完整半音阶**，
含全部升降音。常见简谱曲子无需移调即可完整演奏；只有超出三个八度音域的曲子才受限。

回归保护：`tests/unit/test_instrument_config.py` 已把上述覆盖范围固化为断言
（含边界与「不得出现未实测的组合」）。

### 3.3 配置结构（`config/instrument.json`）

```json
{
  "version": 2,
  "verified": true,
  "verified_at": "2026-09-25",
  "verified_note": "游戏内音阶标注 + Python SendInput 注入实测；修饰键效果可叠加",
  "keys": [
    { "key": "z", "degree": 1, "octave": 0 },
    { "key": "x", "degree": 2, "octave": 0 },
    { "key": "c", "degree": 3, "octave": 0 },
    { "key": "v", "degree": 4, "octave": 0 },
    { "key": "b", "degree": 5, "octave": 0 },
    { "key": "n", "degree": 6, "octave": 0 },
    { "key": "m", "degree": 7, "octave": 0 },
    { "key": ",", "degree": 1, "octave": 1 }
  ],
  "modifiers": [
    { "button": "left",   "label": "降调（降一个八度）", "semitone": -12 },
    { "button": "middle", "label": "半音（升半音）",   "semitone": 1 },
    { "button": "right",  "label": "升调（升一个八度）", "semitone": 12 }
  ],
  "modifier_sets": [
    { "buttons": [], "status": "verified", "note": "无修饰：中音区 1-7 与高音 1" },
    { "buttons": ["left"], "status": "verified", "note": "降一个八度" },
    { "buttons": ["middle"], "status": "verified", "note": "升半音" },
    { "buttons": ["right"], "status": "verified", "note": "升一个八度" },
    { "buttons": ["left", "middle"], "status": "verified", "note": "低音区全部加 #" },
    { "buttons": ["middle", "right"], "status": "verified", "note": "高音区全部加 #" }
  ]
}
```

- 上面就是当前 `config/instrument.json` 的**实际内容**（已实测校准）。
- `semitone: null` 表示尚未校准；`verified: false` 时界面阻止进游戏播放。
- **组合偏移不写死**：`modifier_sets` 只列「允许哪些组合」，偏移由 `modifiers` 求和得到，
  避免同一数值出现两处（回归测试会校验二者一致）。
- 目前列出的组合全部是 `verified`（回归测试会拒绝未实测的组合）；将来若发现新组合，
  先以 `status: "assumed"` 落盘（默认不参与映射），实测通过后再改为 `verified`。
- 校准页与设置页都读写这同一个文件，是键位语义的**唯一权威来源**。

### 3.4 音高映射规则

给定目标音高 `s`（`key_semitone` / `set_offset` 的定义见 §3.2），候选是 `(key, modifier_set)`：

1. 找出所有满足 `key_semitone(key) + set_offset(modifier_set) = s` 的候选。
2. 排序优先级（保证结果确定且可测）：
   ① 只用 `verified` 组合（`assumed` 一律不参与；只有用户在设置里显式启用后才纳入候选）；
   ② 修饰键**数量更少**（0 个 > 1 个 > 2 个）；
   ③ **与上一个音相同的组合**优先（减少鼠标键切换，降低出错与延迟）；
   ④ 键位表顺序靠前。
3. 无候选 → 判定为 **不可达（unreachable）**：编译期报错并带出音符序号与简谱原文，
   界面标红，**不静默跳过、不就近取近似音**。
4. **修饰键组合变化时，一律先松开按键再换修饰键，然后重新按下** —— 即使音高相同。
   理由：游戏是否会在修饰键变化时重新触发同一个键**未知**（U10），重按是唯一不依赖该未知的做法。
   代价是这类转换需要多花约 20–40 ms（受 `note_gap_ms` 与 `modifier_lead_ms` 约束），
   编译器必须在计划里体现，且两音之间留得下这段时间。

## 4. 曲谱格式

### 4.1 文本简谱 DSL（`.kq`，主要创作格式）

```text
# 小星星（示例）
@title 小星星
@tempo 100
@meter 4/4
@key C
@transpose 0

1 1 5 5 | 6 6 5- | 4 4 3 3 | 2 2 1- |
```

**元信息行**：以 `@` 开头，`@title` / `@tempo`（BPM，四分音符=1 拍）/ `@meter` / `@key` / `@transpose`（整体移调半音数）。

**注释**：`#` 到行尾。**小节线**：`|`，仅用于显示与小节校验，不占时间。

**音符** = 音高标记 + 时值标记：

| 部分 | 写法 | 含义 |
|------|------|------|
| 休止 | `0` | 不发声，占时值 |
| 音级 | `1`..`7` | 简谱音级 |
| 变化音 | `#1` / `b3` | 升/降半音 |
| 八度 | `1'` / `1,` | 升/降八度（可重复，如 `1''`） |
| 时值 | 默认 | 1 拍 |
| 时值 | `-` | 每多一个 +1 拍（`5-` = 2 拍） |
| 时值 | `.` | 附点：×1.5 |
| 时值 | `_` | 减半：÷2（`_` 可叠加：`__` = 1/4 拍） |

求值顺序：先 `-` 累加 → 再 `.` 乘 1.5 → 最后按 `_` 的次数除 2。
例：`5-.` = (1+1)×1.5 = 3 拍；`5_.` = (1×1.5)/2 = 0.75 拍。

**连音标记** `~`（写在音符前）：与**前一个音高相同**的音连成一个长音（编译期合并为一次按住）。
用于游戏可能在重复同音时切断的情况；同时也是长音的补充写法。

### 4.2 JSON 曲谱（`.kq.json`，精确存储与交换）

```json
{
  "version": 1,
  "title": "小星星",
  "tempo_bpm": 100,
  "meter": "4/4",
  "transpose": 0,
  "notes": [
    { "start_beat": 0.0, "duration_beat": 1.0, "pitch": 0, "repr": "1", "tie": false },
    { "start_beat": 1.0, "duration_beat": 1.0, "pitch": 0, "repr": "1", "tie": false }
  ]
}
```

`pitch: null` 表示休止。两种格式**往返必须无损**（`.kq` → 内部表示 → `.kq.json` → 内部表示，逐音相等）。

### 4.3 导入来源（v1 全部支持）

| 来源 | v1 | 说明 |
|------|----|------|
| 手敲 / 粘贴文本简谱 | ✅ | 直接进入 DSL 解析器；界面里粘贴即解析 |
| `.kq` 文本文件 | ✅ | 主要创作格式 |
| `.kq.json` | ✅ | 精确存储与交换 |
| **MIDI 文件（SMF 0/1）** | ✅ | 解析为标准 MIDI，再映射到「相对半音 + 拍」的曲谱模型 |
| 图片 / PDF 谱面 | ⏳ M5 | 简谱 OCR 识别率有限，定位为**生成草稿 + 人工校对**，不做全自动承诺 |

MIDI 解析**用纯标准库实现**（SMF 是公开且简单的二进制格式），避免为导入功能引入新依赖
（`AGENTS.md` 要求新增依赖必须先获授权并记 ADR）。导入时需要处理：
多轨合并与通道选择、把绝对 tick 换算为拍、去除打击轨、超出乐器音域的音高（报 `unreachable`）。

## 5. 演奏计划编译

### 5.1 输入 → 输出

输入：曲谱（拍为单位）+ `instrument.json` + `settings.json` 的播放参数。
输出：绝对毫秒的**事件序列**（`runtime/plan.json`，调试产物），由进程内播放引擎逐条执行。

### 5.2 编译算法

对每个音符：

```
start_ms    = start_beat    × 60000 / bpm
duration_ms = duration_beat × 60000 / bpm
hold_ms     = max(duration_ms − note_gap_ms, min_hold_ms)
```

事件（按时间排序）：

1. 若需要修饰键：`mouse_down(modifier)` @ `start_ms − modifier_lead_ms`
2. `key_down(key)` @ `start_ms`
3. `key_up(key)` @ `start_ms + hold_ms`
4. 若有修饰键：`mouse_up(modifier)` @ `key_up + modifier_tail_ms`

后处理：

- **连音合并**：相邻且 `tie=true` 的同音高音符，合并为一次按住（`key_up` 延到后一音结束）。
- **休止**：不产生任何事件，只推进时间。
- **整体移调**：`@transpose` 先加在目标音高上，再做可达性判定。
- **修饰键切换必重按**：相邻两音的修饰组合不同时，先松开键、换修饰、再按下（§3.4 规则 4）；
  这类转换需要额外 20–40 ms，若两音间隔不足则按顺序顺延并在计划里标注。
- **长音切分（长音会自然衰减，见 §2.1）**：当 `sustain_limit_ms` 已测得且某音 `hold_ms` 超过它时，
  在 `retrigger_long_notes = true` 的前提下把该音切成若干段（每段 ≤ `sustain_limit_ms`，
  段间留一个极小的 `note_gap_ms` 重新起音），使长音在游戏内保持可闻；
  若 `sustain_limit_ms` 为 `null`（尚未实测），**不切分**，如实按住整段时值。

### 5.3 计划契约（`runtime/plan.json`）

```json
{
  "version": 1,
  "title": "小星星",
  "tempo_bpm": 100,
  "params": {
    "min_hold_ms": 40,
    "note_gap_ms": 20,
    "modifier_lead_ms": 8,
    "modifier_tail_ms": 8,
    "countdown_ms": 3000
  },
  "notes": [{ "index": 0, "start_ms": 0, "duration_ms": 600, "target_semitone": 0, "repr": "1" }],
  "events": [
    { "t_ms": 0,   "op": "key_down", "key": "z" },
    { "t_ms": 580, "op": "key_up",   "key": "z" }
  ]
}
```

事件 `op` 取值：`key_down` / `key_up`（带 `key`）、`mouse_down` / `mouse_up`（带 `button`）。

**编译期不变量（必须校验，违反则拒绝生成计划）**：

- 所有 `t_ms ≥ 0` 且事件时间非递减；
- 同一键/鼠标键不会在按下状态下被再次按下；
- 计划结束时所有按键都处于松开状态；
- 所有音符的 `target_semitone` 均可达。

### 5.4 控制与状态契约（**已取消**）

原设计的 `runtime/control.json`（命令）与 `runtime/state.json`（状态回写）是**双进程 IPC 通道**。
ADR-003 改为单进程后，播放控制与进度都在进程内完成（线程安全的队列 + 回调），
这两个文件**不再需要**，`runtime/plan.json` 降级为 dry-run 调试产物（仍可用于离线核对与排障）。

进程内的控制语义（与界面一致）：

- `play` / `pause` / `resume` / `stop`，状态：`idle` / `countdown` / `playing` / `paused` / `stopped` / `error`；
- 目标：停止/暂停在 ≤ 100 ms 内生效，且**任何退出路径都不留按下的键**。

## 6. 架构（已按 ADR-003 修订为**单进程**）

原 AHK 双进程方案（ADR-001）已被 **ADR-003：纯 Python 单进程**取代 ——
P0-2 实测确认 Python `SendInput` 在游戏内生效，第二个进程不再必要。
AHK 仅作为「若 Python 路线将来受阻」的备选保留在决策记录中（ADR-001 状态：Superseded）。

```text
┌──────────────────────────────────────────────────────────────────┐
│ 单个进程：python -m kouqin                                        │
│                                                                  │
│  ┌─────────────────┐        ┌────────────────────────────────┐   │
│  │ PySide6 界面     │  控制   │ 播放引擎（专用线程）            │   │
│  │ · 曲谱库/编辑    │───────▶│ · 按 perf_counter 绝对时刻推进  │   │
│  │ · 导入/导出      │◀───────│ · sleep + 忙等（亚毫秒精度）    │   │
│  │ · 播放控制/进度  │  进度   │ · 注入 SendInput（键盘扫描码/鼠标键）│ │
│  │ · 设置/校准      │        └───────────────┬────────────────┘   │
│  └─────────────────┘                        │                    │
│           │                                 │                    │
│           │        ┌────────────────────────▼────────────────┐   │
│           └───────▶│ kouqin/core（纯逻辑）                    │   │
│                    │ 音高换算 · 音高映射 · 可达性 · 计划编译   │   │
│                    └─────────────────────────────────────────┘   │
│  · 全局热键：RegisterHotKey + Qt 原生事件过滤（开始/暂停/停止）     │
│  · 急停保证：任何退出/异常路径都释放全部按下的键                    │
└──────────────────────────────────────────────────────────────────┘
```

模块划分（对应 `AGENTS.md` §5.3）：

| 模块 | 职责 | 关键约束 |
|------|------|----------|
| `kouqin/core/` | 音级/音高换算、音高映射、可达性判定、演奏计划编译 | 纯逻辑，无 Qt、无系统调用 |
| `kouqin/scores/` | `.kq` 与 `.kq.json` 读写、曲谱库索引 | 同上；往返无损 |
| `kouqin/input/` | SendInput 封装（扫描码键盘 + 鼠标键）、按键状态跟踪与释放 | 唯一接触系统输入的地方 |
| `kouqin/player/` | 播放引擎：计划执行、暂停/继续/停止、进度回调 | 不依赖 Qt |
| `kouqin/hotkey/` | 全局热键注册与分发（ctypes `RegisterHotKey`） | 不依赖 Qt |
| `kouqin/ui/` | 曲谱库、编辑器与预览、播放控制、设置、校准 | 只依赖上述模块的公开接口 |

主要风险（单进程方案特有）：

- 界面线程与播放线程的耦合：播放线程不得直接操作 Qt 控件，进度通过信号/队列回主线程；
- 注入精度：已由 `tools/p0_sendinput_demo.py` 验证 `sleep + 忙等` 的时序可用（20 ms 档可稳定触发）；
- 全局热键需要一个消息泵：用 Qt 原生事件过滤接收 `WM_HOTKEY`，实现细节在 Step 2 规格中固化。

## 7. 界面设计（v1）

主窗口：左侧**曲谱库**，中间**编辑/预览**，底部**播放控制条**，顶部菜单（文件 / 播放 / 设置 / 帮助）。

1. **曲谱库列表**：曲名、拍数时长、音符数、映射状态（「可完整演奏」/「N 个音不可达」）。
2. **编辑器**：纯文本简谱；实时解析，错误行高亮 + 消息面板给出行号与原因。
3. **预览**：音符网格（音高 × 时值），不可达音高标红；显示编译后的事件序列摘要（dry-run）。
4. **播放控制条**：开始（带可配置倒计时）、暂停/继续、停止、速度（0.5×–2×）、移调（±12 半音）、循环开关、进度条。
5. **导入/导出**：菜单与拖拽都支持 `.kq` / `.kq.json` / **`.mid`**；也支持从剪贴板粘贴简谱文本（§4.3）。
6. **设置页**：键位表（增/删/改）、修饰键半音数、播放参数、长音重触发开关、全局热键。
7. **校准页**：逐项「试拍」按钮（单独按键 / 修饰键组合 + 按键），用户读数或听音后回填 `instrument.json` 并置 `verified: true`。
8. **状态栏**：运行时状态（未启动 / 就绪 / 倒计时 / 播放中 / 已暂停 / 错误）+ 当前进度。

> 未通过校准（`verified: false`）时，「开始」按钮禁用并提示：`请先在「校准」页确认三个鼠标键的音程`。

### 7.1 全局热键（默认值，设置页可改）

用户明确要求**不使用 F8 / F9**。默认改为带 `Ctrl+Alt` 的组合键：

| 动作 | 默认热键 |
|------|----------|
| 开始 / 停止 | `Ctrl+Alt+P` |
| 暂停 / 继续 | `Ctrl+Alt+U` |
| **急停**（立刻松开所有按下的键） | `Ctrl+Alt+K`（原定 `Ctrl+Alt+L`，2026-09-25 发现被 QQ 占用后更换） |

两点说明：① `RegisterHotKey` 会**吞掉**组合键，游戏不会再看到它，因此不会触发游戏内动作；
② 字母刻意避开口琴键位 `z x c v b n m ,`，避免误触。

## 8. P0 实验（实现前必须完成）

实验工具：`tools/p0_sendinput_demo.py`（**纯标准库**，不需要安装任何依赖）。
所有模式都支持 `--dry-run`（只打印将要发送的事件，不真的注入），便于离线核对。

### P0-1 修饰键音程（对应 U1、U2）—— ✅ 已完成 2026-09-25

**结果**：左键 `−12`、中键 `+1`、右键 `+12`（依据：游戏 UI 的音阶标注，用户逐键读出）。
`compare` 模式**未被使用**，实际采用的是更直接的路径 —— 用户发现游戏会标注当前按下的简谱，
于是「读标注」直接给出了权威答案，比听音对照更可靠。

**组合键（U2）追加结果**：用户实测「按住中键再按住左键」时，在左键的低音八度基础上**所有音都带 `#`**，
即两个修饰键**效果相加**（−12 + 1 = −11）。据此低音区的变化音全部可达，
只用已实测组合就能覆盖 `−12 … +13` 的完整半音阶（§3.2）。
「右键 + 中键」尚未实测（推导为 +13），列入 P0-6。

<details>
<summary>保留下面的做法（供将来换乐器/换游戏时复用）</summary>

**做法 A（零乐理，推荐）：用游戏自己的按键当尺子。**

前提：游戏内这 8 个键是**大调音阶**（简谱 `12345671` 的通常含义）。
在这个前提下：`z→x`（1→2）是 **2 个半音**，`c→v`（3→4）是 **1 个半音**，`m→,`（7→1̇）是 **1 个半音**。
于是只要判断「按住鼠标键时按 `z`」**听起来跟哪个普通键完全一样**，就能倒推出半音数：

```powershell
python tools/p0_sendinput_demo.py compare --button right    # 右键
python tools/p0_sendinput_demo.py compare --button left     # 左键
python tools/p0_sendinput_demo.py compare --button middle   # 中键
```

脚本先弹「按住该鼠标键 + `z`」的参考音，再逐个弹 8 个普通键，重复两轮。
用户只需回答：**参考音跟第几个普通键听起来一样？**（若夹在两个键之间，回答「在 z 和 x 之间」）

| 用户听到 | 结论（该鼠标键的半音数） |
|----------|--------------------------|
| 与第 1 个 `z` 一样 | 0（该键无变调作用或未生效） |
| 夹在 `z` 与 `x` 之间 | +1 |
| 与第 2 个 `x` 一样 | +2 |
| 夹在 `x` 与 `c` 之间 | +3 |
| 与第 3 个 `c` 一样 | +4 |
| 与第 8 个 `,` 一样 | +12（高八度） |
| 比 `z` 低且能找到对应键 | 用同一张表取负号 |

（8 个键的半音表：第 1…8 个键分别是 `0, 2, 4, 5, 7, 9, 11, 12`。）

三个鼠标键各做一次；再做一次「左 + 右同时按住」探是否有额外组合效果（U2）。

> 该表的唯一前提是「这 8 个键构成大调音阶」。若听起来 `z→x` 与 `x→c` 的音距并不相同，
> 说明前提不成立，此时改用做法 B。

**做法 B（完全自动，可选）**：录系统声音 → 提取基频 → `半音数 = 12 × log2(f₂/f₁)`，直接算出结果。
本机没有录音库，需要用户授权安装，或由我用纯 ctypes 实现 WASAPI 环回采集。是否要做取决于做法 A 是否够用。

**做法 C（本次实际使用，最省事）**：若游戏 UI 会标出当前音高（简谱/音名），直接读标注。

### P0-2 哪种注入方式被游戏接受（对应 U7）—— ✅ 已完成 2026-09-25

```powershell
python tools/p0_sendinput_demo.py check     # 先看是否管理员运行、前台窗口
python tools/p0_sendinput_demo.py scale     # Python SendInput 是否生效
```

与 `ssj_yq` 中已验证的 AHK 路线对照。三种结果的含义：

- **Python 生效** → 可考虑单进程纯 Python 实现（部署与测试都更简单），需新 ADR 取代 ADR-001 的运行时部分；
- **只有 AHK 生效** → 维持 ADR-001 的双进程架构；
- **两者都失效** → 先排查权限（游戏以管理员运行时，非管理员进程的注入会被 UIPI 拦截）与注入方式，再重新评估。

**结果：Python 生效** —— `scale` 模式在游戏内触发成功，用户听到完整 8 音上行。
据此采纳 **ADR-003：纯 Python 单进程**，不再使用 AHK（AHK 路线未实测，仅保留为备选）。

### P0-3 最短可按时长（对应 U3）—— ✅ 已完成 2026-09-25

```powershell
python tools/p0_sendinput_demo.py hold-sweep
```

依次用 20 / 30 / 40 / 50 / 80 / 120 ms 弹同一个键（间隔 1.5 秒）。用户记下「第几段开始能稳定听到声音」，
那一段的时长即 `min_hold_ms` 的下限。

**结果**：**第 1 段（20 ms）就能听见**；且后续每一段的音量更大、时长更长（随按时长单调变化）。
含义：① 注入的按下/松开都被游戏识别，`20 ms` 是当前测试下的可听下限；
② 声音时长跟随按住时长，长音可以直接靠「按住」实现（U6 仍待确认是否有上限）。
实现取值：`min_hold_ms` 暂定 **40 ms**（留一倍余量，避免 20 ms 档在不同帧率下偶发丢失），
用真实曲谱回归时再校准。

### P0-4 重复音、最小间隔与长音上限（对应 U4、U6）

```powershell
python tools/p0_sendinput_demo.py key --key z --repeat 8 --hold-ms 60 --interval-ms 20
```

**U4 结果（2026-09-25）**：用户**正常手速连按不吞音**（换算约 120 ms 间隔以上可信）。
更快的连打（`--interval-ms 20`）尚未复测，记为 U11，暂不影响常见节奏
（例如 BPM 120 的十六分音符约 125 ms）。

**U6 结果（2026-09-25）**：长按不会"被硬切"，但会经历完整的气息包络 ——
**渐强 → 出现波浪感（模拟一口气的末段）→ 逐渐变小直至消失**。
也就是说**长音无法靠一直按住来无限延长**，编译器必须支持分段重触发（§5.2 规则 5）。
时间常数尚未量化，见 P0-7。

### P0-5 起始延迟（对应 U5）

用节拍器对照「宏发出瞬间」与「听到声音瞬间」的主观延迟 → `countdown_ms` 与是否需要固定延迟补偿。

### P0-6 「右键 + 中键」组合（对应 U9）

与用户已完成的「左键 + 中键」是同一操作，只需 10 秒：

```powershell
python tools/p0_sendinput_demo.py compare --button right   # 先按住右键；再按住中键试第二个音
```

更简单的做法：在游戏里**同时按住右键与中键**，再按 `z`，看游戏显示的简谱是 `#1̇`（两个八度上方的 `#1`）还是别的。

- 若显示 `#1̇` → 与推导一致，把 `config/instrument.json` 中 `["middle","right"]` 的 `status` 改为 `verified`，
  音域随即可达 `−12 … +24`（放行高音区变化音）。
- 若结果不同（例如右键优先、忽略中键）→ 按其真实行为修正 `modifier_sets`。

**不阻塞**：多数简谱曲子落在 `−12 … +13` 内，P0-6 未测期间高音区变化音会被报为「不可达」。

### P0-7 长音衰减时间常数（对应 U6）

在游戏里按住一个键，心里计时（或用手机秒表）回答两个问题：

1. 大约**几秒开始明显变弱**？
2. 大约**几秒完全听不见**？

也可以用注入方式复现（更接近实际播放条件）：

## 9. 验收标准（v1）

1. **曲谱管理**：可在界面新建/编辑/导入/导出 `.kq` 与 `.kq.json`，往返无损；支持从**剪贴板**粘贴简谱、
   以及导入 **MIDI（.mid）** 并正确转成曲谱模型。
2. **编译正确**：样例曲谱的 dry-run 事件序列与预期逐条一致（自动化测试覆盖，含附点、休止、连音、移调）。
3. **游戏内可演奏**：≥ 3 首曲目（含 `#`/`b` 变化音、休止、长音）音高与时值主观正确；
   **长音在游戏内保持可闻**（`sustain_limit_ms` 测得后由重触发保证）。
4. **控制可靠**：停止在 ≤ 100ms 内生效；停止或异常退出后不留按下的键/鼠标键。
5. **错误可见**：语法错误与音高不可达在界面明确报出（行号 / 音符序号），不静默跳过。
6. **未校准保护**：`verified: false` 时阻止进游戏播放并给出明确提示。
