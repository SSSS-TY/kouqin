# ERR-003: 焦点守卫连续两次误判（最终根因：Win32 函数缺少 ctypes 签名，句柄被截断）

- **发现时间**: 2026-09-25
- **发现者**: User（两次实机反馈）
- **状态**: Resolved
- **影响范围**: 焦点守卫（演奏能否开始、是否误判为「焦点离开」）；不影响曲谱解析与编译
- **关联任务**: v1 实现 —— M3 播放引擎
- **关联决策**: ADR-005（输入安全边界）

## 错误现象

1. 第一次：「焦点守卫有问题，现在无法播放了」——点开始毫无反应。
2. 第二次：已改为「在窗口里点开始」，仍报 `焦点离开了目标窗口，已停止演奏并释放所有按键`。

## 复现步骤

1. 界面里点「开始」→ 3 秒倒计时内切回游戏；
2. 出现上述提示，演奏未开始（第一次则是完全无反应）。

## 分析过程

- **假设 1（第一次）**: 守卫在**尚未锁定目标窗口**（`target == 0`）时就把 `ok()` 判为 False，
  于是倒计时一开始就被当成「焦点离开」而中止。
  - **验证**: 阅读 `FocusGuard.ok()` 与 `Player._wait_until` 的调用时序 → 成立。
  - **修复**: 未锁定时一律返回 True（不拦截）。
- **假设 2（第二次）**: `GetForegroundWindow` / `GetWindowThreadProcessId` 未声明 ctypes 签名，
  64 位下 `restype` 默认按 32 位 int 处理 → **句柄被截断** → `window_pid()` 取不到进程号（返回 0）→
  「前台是本程序」这条检查**永不成立** → 守卫把本程序自己的窗口当成了目标窗口；
  用户切回游戏后前台变化 → 立刻报「焦点离开」。
  - **验证**: 检查 `kouqin/input/win32.py`，确认只有 `SendInput` 声明了 argtypes/restype，
    其余窗口 API 均为默认（`c_int`）→ 成立。
  - **修复**: 显式声明四个窗口 API 的签名；并规定「取不到进程号时宁可拒绝」。

## 已尝试方案

### 尝试 1

- **修改或操作**: `ok()` 在 `target == 0` 时返回 True。
- **结果**: 修复了「无反应」，但暴露出第二个误判。
- **新证据**: 用户第二次反馈的提示变成了「焦点离开」。

### 尝试 2

- **修改或操作**: 补齐 Win32 签名、进程号取不到时拒绝、新增焦点宽限 1.2 秒、
  提示中带上「目标窗口 vs 当前前台」标题。
- **结果**: 通过。用户确认「现在界面的启动也可用了」，随后 MAN-08/MAN-09 实机通过。
- **新证据**: 截断假设被签名修复后的行为证实。

## 根本原因

`ctypes.WinDLL` 未声明 `restype` 时按 `c_int` 处理返回值，而 64 位 Windows 的 `HWND` 是指针宽度；
句柄被截断后传给 `GetWindowThreadProcessId` 得不到正确进程号，导致「前台是本程序」的安全检查失效。

## 修复方案

1. `kouqin/input/win32.py`：为 `GetForegroundWindow`、`GetWindowThreadProcessId`、
   `GetWindowTextW`、`GetClassNameW` 声明 argtypes/restype。
2. `FocusGuard.capture()`：进程号取不到（0）时**拒绝**，不把未知窗口当成合法目标。
3. `Player`：新增焦点宽限 `focus_grace_s`（默认 1.2 s），宽限期内切回来继续演奏并补回等待时间。
4. 提示与 `check` 命令输出目标/当前窗口标题，便于定位。

## 经验教训

- 涉及 Win32 API 的 ctypes 调用**一律显式声明 argtypes/restype**，否则 64 位下会出这类静默截断。
- 「安全保护」必须先写清它的**中立状态**（未上锁时不拦截），否则会把功能整个挡住；
  两次故障都是守卫在「不该管的时候」做了判定。
- 这类缺陷必须用**纯逻辑测试 + 真实调用替换**覆盖（`tests/unit/test_focus_guard.py` 与 `E-12/E-13`）。
